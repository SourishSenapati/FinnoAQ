7. STATISTICAL AND SCIENTIFIC ANALYSIS ENGINE
======================================================================
Make the statistical engine modular and data-gated. Implement only methods whose assumptions and data requirements are met.

7.1 Baseline descriptive analysis
- Group by source-defined sample group, lot and assay. Report number of independent lots, biological/technical replicates, exclusions and missingness distinctly. Never count multiple technical readings from one physical sample as independent commercial lots.
- Report means/SD where suitable, median/IQR where distributions warrant, uncertainty intervals, distributions and individual data points where confidentiality allows.
- Plot all key parameters with units, n and uncertainty. Include within-lot and between-lot variability when available.

7.2 Comparative inference
- Identify the experimental unit and primary endpoint before inference. Use Welch's test for suitable independent comparisons, paired methods only for genuinely paired design, and mixed-effects/hierarchical models when lot, batch, operator or repeated measures require them. Check assumptions and provide robust/nonparametric or bootstrap sensitivity analysis when appropriate.
- Report absolute differences, relative differences only when meaningful, standardized effect sizes, 95% confidence/credible intervals, exact test statistic, degrees of freedom, p-value, group n, and multiplicity adjustment such as Holm or Benjamini–Hochberg where a family of tests exists.
- Do not convert a p-value into a probability that the mechanism is true. Do not equate significance with practical importance. Do not infer causality from a cross-sectional group contrast.
- If n is too small or there is only one lot per group, make limitations explicit and do not present pseudo-replication as population evidence.
- Keep SOW Categories A–D as a synthesis taxonomy: A = directly measured difference supported by data/QC; B = meaningful observed association; C = plausible mechanism needing validation; D = evidence does not support meaningful involvement. State the scope of tested lots and uncertainty for each label.

7.3 Hydration and Peleg model
- Fit only to actual hydration measurements with time, mass/moisture uptake, conditions, sample/lot and replicate provenance. A conventional Peleg representation may be evaluated as `M(t) = M0 + t/(k1 + k2*t)` (with units defined from the response/time units); its derivative can be used only when mathematically and dimensionally consistent. Validate the exact parameterization and units against the data and chosen definition.
- Fit an interpretable nonlinear model (e.g. SciPy curve_fit/least squares with bounds and residual diagnostics) as the default. Estimate uncertainty and assess identifiability/correlation of parameters; bootstrap at the correct experimental-unit level if data permit; compare with a baseline model and held-out predictions if there are enough observations.
- Do not initialize a neural net with guessed target curves and then call parameters “measured” or “discovered.” Do not create a PINN by default. Use a PINN only if real observations, a justified physical equation, identifiable parameters, a valid residual/boundary formulation, and baseline comparison justify it. Validate on holdout data and report when the more complex model does not help.

7.4 Root-cause synthesis
- Use a claim ledger: claim ID, exact statement, classification, source data rows, analysis function/version, uncertainty, alternative explanations, contradiction/limitations, and Phase 2 validation required.
- Separate correlation, mechanism plausibility, and causal evidence. Include the strongest disconfirming evidence and factors not measured.
- Literature can contextualize but cannot substitute for missing experimental results. Distinguish prior published evidence from data on Harakutir's specific lots.

11. GPU/CPU RESOURCE POLICY — RYZEN 9 + RTX 4050-CLASS
======================================================================
- Discover actual hardware. Assume nothing about VRAM, core counts, drivers, laptop thermal limits, CUDA support or free disk.
- Use CPU for ingestion, general statistics, report building and most scientific calculations unless benchmarking demonstrates a GPU advantage. Reserve GPU for workloads that actually benefit, e.g. supported model inference, vectorized simulations or numerical workloads with enough scale.
- Cap GPU use conservatively using observed free VRAM. For a 6 GB GPU, target roughly 3.5–4.2 GB for this project's optional model workload and preserve headroom for display/other applications; this is a policy target, not a guarantee. Enforce batch-size/context-length limits and detect out-of-memory errors with safe fallback/retry at smaller settings.
- Default to one GPU-consuming task at a time. Bound CPU process/thread counts to leave the machine usable. Prevent BLAS/OpenMP oversubscription by recording and setting suitable thread limits.
- Prefer FP32 for numerically sensitive fitting/statistics; use FP16/BF16 mixed precision only where hardware support and numerical stability are demonstrated. Never trade away scientific accuracy merely to use the GPU.
- Sample `nvidia-smi`/process telemetry only if available. Pause or reduce workload when configured thermal, memory, power or responsiveness limits are exceeded. Make thresholds configurable and log all throttles.
- Before model downloads, check size, license, hardware fit and genuine utility. Do not install or train a giant LLM just because the GPU can run for days. No external paid API by default; no confidential data sent to an LLM cloud service.
- Do not run an artificial endless stress test or waste GPU cycles. A long run must have explicit task count/budget and quality-based stopping criteria.
